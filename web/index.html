In short

DeltaConv learns on point clouds with gradients that live in each point’s tangent plane. Its authors argue the result does not depend on which tangent basis you pick at each point, and the continuous maths agrees.

The discrete implementation makes two numerical choices, a ridge penalty and a gradient normaliser, that each quietly reintroduce the basis. Rotating every tangent frame moves the normalised gradient by 2.08 % on average over 72 synthetic conditions, and by up to 10.2 % in the worst one.

Two small changes bring that drift down to 10−15, which is floating-point noise. They do not make the gradient more accurate. Nothing on this page measures a trained network either.

Directions on a surface need a frame

DeltaConv [1] runs two streams of features side by side. A scalar stream stores one number per point and channel. A vector stream stores a direction per point and channel, and the network moves between them with geometric operators: gradient, divergence, curl. This lets it pick up anisotropic patterns, like an edge or a ridge, while working directly on the point cloud.

A direction in the tangent plane is stored as two numbers. Two numbers only mean something relative to a pair of axes, a tangent basis (u, v), and on a point cloud nothing singles out one basis over another. The implementation picks one per point by a fixed rule. Any rotation of those axes would have been just as legitimate.

Coordinate independence is section 3.7 of the paper. Rotating the axes by θ should rotate the two coefficients by −θ and leave the actual 3D arrow unchanged.

The first quantity DeltaConv needs is the gradient of a scalar field. Below is the one used throughout this audit, f(x,y,z)=\sin 2x + yz/4, sampled on 512 points. The arrows are estimated by the method described next; switch to the exact gradient to compare.

How the gradient is estimated

DeltaConv estimates gradients with weighted moving least squares. For every point it takes its 20 nearest neighbours, including itself, writes their offsets in the local frame as (u_j, v_j), and fits a quadratic polynomial to the field values:

f(u,v) \approx c_0 + g_u\,u + g_v\,v + a\,u^2 + b\,uv + c\,v^2

The linear coefficients (g_u, g_v) are the gradient in that frame. The fit minimises a Gaussian-weighted squared error. On thin or lopsided neighbourhoods the problem is badly conditioned, so the paper adds a small ridge term [1, §3.2]:

\min_{\theta}\; \sum_j w_j\,\big(f_j - B_j\theta\big)^2 + \lambda\,\theta^{\top} P\,\theta, \qquad \lambda = 10^{-3},\; P = I

The gradient is then rescaled by a single global number so that features stay in a reasonable range from one layer to the next. Both steps make sense. The catch is that each of them looks at the coordinates.

Where the basis sneaks back in: the penalty

Take the quadratic part a u^2 + b uv + c v^2. It is a symmetric tensor in disguise:

H = \begin{pmatrix} a & b/2 \\ b/2 & c \end{pmatrix}, \qquad \|H\|_F^2 = a^2 + \tfrac{b^2}{2} + c^2

Rotating the frame turns H into R^{\top} H R. The Frobenius norm survives the rotation, but the identity penalty a^2+b^2+c^2 is not that norm. It counts the mixed term twice as heavily, so the same surface patch pays a different price depending on how the axes happen to sit. Turn the dial and watch.

The fix changes one entry of the diagonal: P = \operatorname{diag}(1,1,1,1,\tfrac12,1), which penalises exactly \|H\|_F^2. On its own this already makes the raw gradient basis-independent to machine precision in every one of the 72 conditions.

The constant term is still regularised, so the gradient of a constant signal is not exactly zero at λ > 0. Polynomial reproduction is tested separately at λ = 0.

Where the basis sneaks back in: the normaliser

For each point the MLS fit produces a stencil: one small 2D vector g_{ij} per neighbour, telling how much neighbour j contributes to the gradient. To normalise, the upstream code sums the absolute values of each component separately, then takes a norm:

s_{\text{upstream}} = \max_i \Big\| \Big(\textstyle\sum_j |g_{ij}^{u}|,\; \sum_j |g_{ij}^{v}|\Big) \Big\|_2 \qquad s_{\text{invariant}} = \max_i \textstyle\sum_j \|g_{ij}\|_2

Absolute values per axis are an L1 measurement, and L1 depends on the axes. The same arrows measure longer when they sit diagonally. The invariant bound only adds arrow lengths, which no rotation can change.

The whole cloud, live

The audit’s test is blunt. Points, normals, neighbours and signal stay fixed, and every point gets an independent random rotation of its tangent frame. Then I recompute the normalised gradient and measure how far it moved. A basis-independent operator should not move at all.

The numbers are computed in your browser, and at the end of the slider they match the recorded measurement. The upstream colour is nearly uniform because most of its drift comes from the single global scale, which shifts every arrow at once.

Across 288 measurements

I fixed the protocol before running anything. There are two analytic surfaces, a unit sphere and the saddle z = 0.3(x^2 - y^2). Sampling is uniform or 90/10 biased, with three noise levels, three seeds, and exact or PCA normals. That makes 72 conditions, and each one goes through four methods that change one thing at a time.

The penalty alone (B) removes the drift of the raw gradient, but the upstream normaliser keeps the normalised one moving. C removes both. Accuracy against the exact gradient barely changes, and on average it is very slightly worse: 16.39 % against 16.33 %. The fix buys invariance. It does not improve accuracy.

The local width of D lowers the error on the deliberately sparse halves of the clouds, from 18.77 % to 17.14 %, while raising it overall. That average mixes uniform and biased clouds, so filter Figure 5 to biased 90/10 before drawing conclusions about undersampled regions. I treat D as an exploratory ablation.

What this does not show

  • No trained network was run. The audit transcribes the gradient formulas of the official code to NumPy. Classification accuracy, learned robustness and GPU speed were not measured.
  • The PyTorch parity check is still pending. scripts/check_upstream.py compares against the official implementation, but it needs PyTorch and PyG, and neither was installed in the audit environment.
  • The 72 conditions are controlled variations of two analytic surfaces, not 72 independent objects, so I make no claim of statistical significance across shapes.
  • Tangent-basis independence is a different property from rotation invariance. The official model feeds raw xyz positions as features, and those change when the object turns. This audit says nothing about that.
  • Swapping the normaliser in a checkpoint trained with the other one will not improve it. The two scales differ, so evaluating the fix as a network change would need retraining.

Reproduce it

The CPU audit needs only NumPy and runs in about nine seconds. All the figures on this page read their inputs from that same run.

python -m pip install -r requirements.txt
python -m pytest tests -q
python -m deltaconv_audit.experiment --output results/runs/my-audit --points 512 --seeds 0 1 2
